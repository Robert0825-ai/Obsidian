## 设计原因

你要的其实是 Godot 的默认做法，不是偏方：

1. **场景当模块**：玩家是一份 `.tscn`，关卡里「实例化」它。拖进去就能跑。  
2. **碰撞跟身体走**：`CharacterBody2D` + `CollisionShape2D` 在玩家场景里，带到哪一关都还在。  
3. **数字写在检查器**：`@export`，不是写死在公式中间。  
4. **自己做调参插件：现在不合适。** 检查器已经在拧这些数。插件是给「引擎没有的按钮」用的，不是给 `speed` 用的。

担心「拆开会更卡、手感更差」：对你这种 2D 横版、一只猫几块地，**场景模块化几乎不伤性能，也不改手感公式。** 手感差来自数字和 `move_and_slide` 怎么写，不来自「玩家是不是单独一个场景」。

## 三句话对错

| 想法 | 对不对 | 人话 |
|------|--------|------|
| 玩家做成模块，拖进关就能跑、碰撞跟着走 | **对，而且测试场已经这样** | Godot 叫「场景实例化」 |
| 加新角色方便 | **对，但第一款先别加第二个可玩角色** | 复制玩家场景、换 `Visual`、数字可以不同 |
| 数值写在引擎里手动改，不写死在逻辑缝里 | **对** | `@export`，选中玩家看右边 |
| 再写一个插件专门控制数值 | **现在不合适** | 和检查器重复；费时间；不让手感变好 |
| 模块化会让性能/手感变差 | **你这体量不会** | 卡如果出现，先查图太大、每帧 new 东西，不是「拆成场景」 |

## 加角色时真正方便的做法

```
test_player.tscn     ← 身体 + 碰撞 + 脚本（一份）
  Visual/            ← 以后换猫图
关卡.tscn
  实例化 test_player ← 拖进来
```

新角色（以后，比如 C 只是 NPC）：

- NPC：新场景，**不要**复制整份跳冲滑。站着说话即可。  
- 第二个可玩角色：复制 `test_player.tscn`，换外观，检查器里拧另一套速度。脚本尽量共用。

第一款仍是一只 A。模块是为了**换皮和摆关方便**，不是为了现在做三人小队。

## 数值：检查器够了，插件以后再说

Godot 已经有三层，从浅到深：

| 层 | 是什么 | 什么时候用 |
|----|--------|------------|
| 1 `@export` | 脚本顶上的数，出现在检查器 | **现在。测试场已经在用。** |
| 2 `Resource`（`.tres` 文件） | 一份「数值卡」，猫和以后的怪可以各持一张 | 数字变多、要共用/存档时 |
| 3 编辑器插件 | 自己做停靠面板 | 引擎真的没有这个按钮时 |

自己写插件：**能**做调参面板；它真正强的是给团队做专用工具，不是让 `jump_velocity` 更准。和当前差距：检查器已经能拧。简单替代就是选中玩家改 `@export`。你以后要学插件可以，**测试场手感稳之前不要开这个坑。**

## 性能（短）

一只 `CharacterBody2D`、一座测试场、几个 `StaticBody2D`：这是 Godot 舒适区。  
模块化 = 多几个节点，开销可以忽略。  
真会卡的：每帧 `instantiate` 又不删、1024 大图铺满屏、在 `_process` 里找全树。那是以后的课，不是今天。

手感：同一套 `speed` / `jump_velocity`，写在检查器或写在代码里，**跑起来一样。** 检查器只是改数的地方，公式还在 `_physics_process`。
